# Family Search and Identity Tags Update Plan
10 November 2026 — Revision 3, implemented and locally validated

## Goal and baseline
Use GlobalVillage_Azure_Team_20261110.zip as the new integration baseline. Add person-name search to the group-based Family tree, introduce coloured family/personal tags, and improve Family module boundaries. Preserve teammates' Azure configuration and unrelated Auth, Community and Chat behaviour. Implementation is complete and locally validated. Production deployment has not been performed. Baseline descriptions below describe the supplied version before this update.

The supplied source already contains a separate Family API/SQLite store, authenticated membership, group-based tree connections and a zoomable canvas. Tree snapshots deliberately omit other families' private member records. Family membership stores realName and kinship; family and membership identity tags are not implemented. Activity records have a separate tags field which must retain its existing meaning. The public URL could not be inspected through the web-reading tool, so source/live-version parity remains unverified.

## 1 Person search, visibility and location
- Place Search by name at the top of both the tree overview and large canvas. Search only the selected tree's current connected component. Match membership real names, ignoring case and surrounding/repeated spaces; support partial matches and Unicode names.
- All current members of linked families are visible by name by default to members of that connected tree. No individual opt-in switch is required. Keep access restricted to the connected tree; names are not made publicly searchable. Existing administrator approvals for linking/merging families remain required.
- Search results show the person's name on the left and tags on the right, with family tags first and personal tags second. Show the family name as secondary identification even when no tags exist. On narrow screens allow tag wrapping without changing their order. A person in multiple families has one result per membership; people sharing a name remain distinct.
- Add individually addressable member-name rows inside each family node. Use stable groupId plus member identity keys, never name text, to locate a row. Selecting a result expands the relevant member list if needed, waits for layout, and animates the viewport centre to that exact name row at a readable zoom. Highlight both the row and its containing family. On the overview, open the large canvas with the same selected membership. Do not merely centre on the family's heading or change the primary-family preference.
- Retain all connection lines and other families. Recalculate node sizes and edges when member lists expand, tags wrap or text scaling changes. Provide Show all, clear-search, loading, no-match and retry states. Debounce queries, paginate bounded results and discard stale responses.
- Cross-family search responses include only the display name, family identity and family/personal tags needed for this feature. Do not include health notes, contact information, private activities or authentication identifiers. Revalidate membership and connectivity for every query and selection. After leaving, disconnection or removal, obsolete results and open member panels lose access and are cleared when the change is received or the next refresh/request occurs.

## 1A Connection notifications
- When the final required administrator approval successfully creates a link, persist an in-app notification for current members of every affected family in the newly connected component. Pending/rejected/cancelled proposals must not send a connection-success notification.
- State which families were linked and that names and display tags are now visible within the connected tree. Opening the notification loads the current authorized tree. Use an idempotent event/outbox with per-recipient delivery/read state so retrying cannot create duplicate notifications or roll back an otherwise successful link.
- Show an unread indicator in Family and support read/unread tracking. Initial delivery uses refresh or lightweight polling while Family is active; no claim of operating-system push, email or external messaging. Members joining an already linked group see the same visibility explanation during joining. Administrators see it before proposing/approving a link.

## 2 Family and personal tags
- Family tags describe the group, for example White Family or John's family. Owners/admins create, edit, recolour, reorder and remove them. All group members see the same family tags.
- Personal tags describe a user's identity in that specific family. Use optional label/value entries, for example Name: John and Gender: Male, plus custom entries. Name may reuse the existing membership real name instead of storing a conflicting second name. Gender is optional and self-described; no inferred values or compulsory disclosure. A tag never changes the real membership role or administrator permission.
- Create family: enter the existing required family/name/relationship fields, add family tags and personal tags, choose colours, preview and save together. Tags are optional.
- Join family: preview existing family tags read-only, then choose/add personal tags before joining. Joining members cannot overwrite shared family tags. Existing members edit personal tags through My family profile; administrators maintain shared tags through Family settings.
- In profile/description areas, family tags appear only before the family description, and personal tags only in that member's personal introduction. Do not add My tags to the shared family description. Add an optional per-membership personal introduction if none exists. In search results, combine the two kinds only as explicitly requested: family tags followed by personal tags beside the name. Explain during create/join/profile editing that these display tags can be seen by members of connected families. Do not modify the unrelated global Profile module.
- Offer exactly 30 named preset colour choices. Use varied hues/lightness, a visible selected marker and automatically contrasting text. Always retain text labels so colour is not the only distinction; do not claim all 30 colours are equally distinguishable for every viewer. Store stable palette IDs, not arbitrary CSS.
- Proposed limits: 5 family tags per group, 5 personal tags per membership, 30 characters per label and 60 per optional value. Trim input, reject empty/duplicate entries, render as plain text, and wrap long rows on phones. Old records show no tags and remain usable.

## 3 Architecture and migration
- First compare the November archive with the current local source and record intentional differences. Review archive configuration without executing its scripts or copying secrets. Do not overwrite Azure changes with older October deployment settings.
- Refactor incrementally within Family: separate page widgets, search/canvas state, typed data models and the Family API repository. Extract reusable tag editor/chip/palette components. Keep temporary exports/adapters for existing navigation and tests instead of a disruptive project-wide file move.
- On the backend, separate search authorization/query logic, tag validation/storage and tree connection logic behind Family service interfaces. Reuse Auth solely to validate user identity; do not read/write Auth, Chat or Community databases from Family.
- Add dedicated family-tag and membership-tag tables, per-membership introductions, notification delivery/read-state tables, indexes and versioned additive migrations. Existing create/join operations and their tags must commit atomically. Use parameterized queries and bounded searches. Proposed endpoints include GET /families/:id/tree/people, administrator family-tag updates and self-only member-tag/introduction updates and notification reads. Final names follow the existing API conventions.
- Inspect existing positional INSERT statements before changing schemas. Preserve existing memberships, invitations, records, approvals and connection codes. Keep a database backup and a tested restore path; do not reset production data. Validate migration against a sanitized copy and ensure a previous compatible app build can still read the database.

## 4 Demonstration family and removing links
- Provide an explicit Add demo family action in the local/demo environment. Create a clearly labelled fictional group called John Prince Family with exactly five fictional display members: John Prince, Emily Prince, Daniel Prince, Olivia Prince and William Prince. Mark the group and members as Demo data. Use English labels and sample tags for search presentation; do not create real Auth accounts, passwords or invitations for these people.
- Keep demo provisioning and storage isolated from normal live families. The demo uses the same search/render/tag behaviour, but its approval simulation and virtual members are available only in the demo environment. Never insert it automatically into every user's tree or seed the Azure production database on startup. Creation is repeat-safe and the UI can remove the demo again.
- Include Disconnect family in the development list and verify/extend the existing backend disconnection capability rather than implementing a competing mechanism. In Manage, an administrator of either endpoint family selects a direct link; display both family names and the resulting branch split, then confirm and remove that edge transactionally. Other connections and both families' members, tags, activities and records remain intact. An ordinary member cannot disconnect groups.
- The demo's direct link can be removed through the same interaction. A separate Remove demo family action deletes only marked synthetic fixtures in the demo environment after confirmation; it is not the normal unlink action.
- Notify affected members of a successful disconnection, invalidate affected pending proposals, and revalidate search results and open views. In the existing acyclic graph, removing one edge splits the component into two; access to people on the other branch ends while access through remaining valid memberships is preserved. Re-linking real groups requires a new approval workflow.

## Acceptance checks
1. Name search shows names on the left and family tags then personal tags on the right. Selecting a result centres the exact member-name row, including expanded groups, mobile widths and larger text settings.
2. All linked family members are discoverable by default within their connected tree. Outsiders and disconnected branches cannot enumerate names, tags or private records; every selected result is revalidated.
3. Linking notifies all affected current members only after successful final approval. Repeated delivery does not duplicate notifications; unread state survives restart. Disconnection also notifies affected members.
4. Family tags appear in family introductions and personal tags in personal introductions; neither is mixed into the other description. Create/join edits persist and enforce administrator/self-only permissions. All 30 colour choices remain labelled and readable.
5. John Prince Family contains exactly five clearly fictional English-named members, supports search and manual unlinking/removal, and cannot be automatically seeded into production.
6. Disconnect removes the selected direct edge without deleting real family records. Tree branches, pending requests, search visibility and notifications update consistently.
7. Relevant Family tests and Auth/Chat/Community smoke checks pass; inherited failures are reported separately. Additive migration and restore are verified before deployment.

## Confirmed product decisions
The user confirmed default name visibility for linked families with member notification, separate personal/family introduction tags, combined ordered tags in search results, exact-person viewport centring, and a removable fictional demo family. These replace Revision 1's proposed opt-in search policy. Other size limits and the isolated demo approach remain implementation defaults in this plan. Application UI and coursework documentation remain English. Revision 3 records completed implementation; Azure remains unchanged.
